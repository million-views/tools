# S11: read-only live session identity

Historical investigation. Current policy is in spec sections 4 and 6; the
Codex daemon query is deferred. See [v1 verification](v1.md) for implementation.

Authorized after the M0 report. Investigation on 2026-11-10; no production code
or M1 work. The owner performed the in-agent changes in disposable test sessions.
No agent/configuration files were edited and no desktop commands were automated.

## Claude: a usable runtime mapping was found

The installed agent writes `~/.claude/sessions/<pid>.json`. Every one of the 11
live Claude processes in the sample had a matching record. The identity fields
are `pid`, `sessionId`, `procStart`, `cwd` and `version`; other fields are not
needed. In particular, do not read `.key` files or retain peer credentials, socket
paths or session names. The saved fixture is a projection, not a raw complete
record containing these unrelated values.

The process-start strings are UTC: reading ps in the local time zone initially
produced a seven/eight-hour mismatch, while `LC_ALL=C TZ=UTC` matched all 11
records after whitespace normalization. Use start identity as well as PID to
reject stale records. Each registry session had one matching top-level transcript
and its recorded session ID agreed with the registry within the first 200 lines.
Three live processes in one project had distinct registry session IDs. The final
probe took 9.298 ms including metadata/transcript checks, excluding ps; this is
one measurement, not the 50-pane performance acceptance test.

The owner supplied a known session ID, resumed it, and then ran `/clear` in PID
52702. The record initially agreed with that supplied ID. After `/clear`, the
same PID and process start had a different registry ID, while `ps args` continued
to contain `--resume` with the old ID. This is direct evidence against elevating
argv to exact and for prioritizing runtime metadata.

Reproduce the passive check without desktop changes:

```sh
LC_ALL=C TZ=UTC ps -A -ww -o pid=,ppid=,tty=,lstart=,args= |
    python3.14 tsr/scripts/m0-live-claude.py
```

The helper reads agent files and prints already anonymized JSON. Preview its
output before saving. Session aliases and cwd aliases preserve equality within
that report; aliases are not stable across captures. It projects only identity
evidence and checks transcripts without emitting any prompt contents.

Design change recorded in the spec: add `live-metadata` before `open-file`;
delegate to the adapter's `session_from_runtime(pid, start_utc)`. For Claude,
require the live executable match, matching PID/file name, matching start,
valid session ID, one matching transcript, and agreement with its recorded ID.
Failure of any check falls through to the existing strategies. Read the runtime
metadata on every capture; do not cache a session ID across in-agent changes.
This adds file reads, not another subprocess, and keeps core code agent-neutral.

Limits: observed registry versions are 2.1.316–2.1.322. This is not an upstream
stability promise. In-session `/resume`, exit cleanup and deliberate PID reuse
were not exercised. The future implementation must reject mismatches rather
than assume every file is current. The ordinary capture/live-restore race also
remains: this evidence is identity at capture time, not an atomic lock shared
with every agent launcher.

## Codex: writer ownership found, terminal ownership unresolved

Direct lsof inspection of the three CLI processes showed no transcript or
session-named writer lock. A directory-scoped read-only lsof probe instead found
three `thread-writer-locks/<session-id>.lock` descriptors in shared daemon PID
32138. One named the owner's supplied test session. Other lock metadata matched
real rollouts; two of the three sessions shared the current project, so cwd
cannot determine which CLI owns which one.

The owner used `/new` and sent a harmless prompt in test frontend PID 52277.
Afterward:

- the frontend PID and process start were unchanged;
- its command line still named the old session;
- the shared daemon retained all three previous locks and added a fourth.

The lock set therefore cannot by itself distinguish the terminal's current
session from retained server state. It may be useful for conservative duplicate
blocking, but neither completeness nor current frontend association is verified.
Both lsof commands returned exit 1 while emitting descriptor rows; do not treat
the result as a proven exhaustive list of running sessions.

The inspected `state_5.sqlite` threads schema has session metadata but no PID
column. The logs schema has `thread_id` and `process_uuid`, with no verified
mapping from that UUID to a CLI PID. Merely correlating timestamps would recreate
the heuristic ambiguity this spike is intended to remove.

Reproduce the lock observation (read only):

```sh
LC_ALL=C lsof -n -P +D "$HOME/.codex/thread-writer-locks" -Fpn
```

The output needs path/session-ID anonymization and preview before saving. The
schema fixture contains only column names. Its final inspection used SQLite
`mode=ro&immutable=1`, which does not participate in live WAL visibility; it is
schema evidence, not a fresh-session query. No database was changed, checkpointed
or migrated. Existing Codex argv/recent/picker fallbacks remain in the design.

## Codex follow-up: loaded-session enumeration works

Official [app-server documentation](https://learn.chatgpt.com/docs/app-server)
describes initialization, loaded-thread enumeration and metadata reads that do
not resume or subscribe to a thread. A stdlib client was then tested against the
existing default Unix control socket, without launching a server or calling
start/resume/turn methods.

The measured response enumerated three loaded IDs, including idle threads.
`thread/read` of the previous `/new` test session returned `notLoaded`; a second
loaded-list query confirmed that reading it did not load it. The final capture
took 2.977 ms. Metadata had no PID fields; `extra` was null and environment
metadata did not expose frontend identity. Multiple loaded threads shared a cwd.

This supplies loaded-ID evidence without solving terminal association. Whether
it should block or warn was not decided by the probe; current tsr does neither
because the query is deferred. It does not establish
coverage of other servers or standalone CLI versions. A missing socket, failed
query or absent ID is not proof that no other runtime has the session open.
It also does not make a guessed terminal/session pairing exact. This is local
Unix IPC, not an external network connection; a future implementation needs an
injectable transport and explicit coverage rather than treating every failed
or empty query as "nothing running".

Reproduce the passive probe:

```sh
python3.14 tsr/scripts/m0-codex-read.py
```

For the old-thread non-loading check, add `--previous-test-session YOUR_OLD_ID`
for an existing, already unloaded disposable thread. The emitted report contains
only aliases, statuses and field shapes. All unprojected metadata stays in memory.
The probe's method allowlist excludes all session-changing operations.

## pi: no verified passive mapping found in the inspected sources

The actual installed package is `@earendil-works/pi-coding-agent` 1.5.1. The
launcher resolves to the managed release under `~/.pi/agent/install/releases/`.
Inspecting this package was necessary: the older package path referenced by the
original spec is not the installed source path.

CLI setup explicitly sets `process.title = APP_NAME`, consistent with the bare
`pi` observed in ps even after `--session`. SessionManager holds its session ID
and file as object fields, writes records synchronously, closes explicit file
descriptors, and appends later records with `appendFileSync`. Idle lsof showed no
transcript handle. No PID/session sidecar was found in the inspected core code
or the default session directory.

The installed RPC client's `start()` launches another process using `--mode rpc`
and pipe stdio. That is not evidence of an attach interface for this running
interactive pi. It was inspected, not invoked. No extension was installed,
configuration changed, process debugger attached, or terminal input sent.

This does not prove every possible read-only mechanism is impossible. It means
there is still no verified interface on which tsr can base exact pi identity.
The existing argv/recent/picker fallback is retained, with S2's known limits.

## Limits and subsequent policy

S11 supports exact Claude capture in the sampled versions and one daemon's
loaded-ID enumeration. It does not establish passive Codex/pi frontend identity
or universal duplicate prevention. No hooks, wrappers or integrations were added.

The owner subsequently chose scoped blocking and explicit uncertainty warnings
instead of a universal guarantee. Picker rows remain unverified. S5 and private
S8 still require external account/publication checks; see [v1 verification](v1.md).
